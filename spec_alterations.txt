Spec Alterations
================

1. Graph Connectivity (implemented)
-----------------------------------
Problem: Walk graph has disconnected components causing zero-score anomalies.
Solution: Filter graph to largest connected component before snapping POIs and grid points.

2. Kernel Decay Rate (implemented)
----------------------------------
Problem: Exponential kernel with lambda=300m decays too slowly, causing high scores
to "bleed" into areas like the Charles River where walking access is limited.

Original spec: lambda=300m
Selected: lambda=120m (after comparing 100-200 range)

Decay at λ=120m:
- 50m:  66% weight
- 100m: 43% weight
- 200m: 19% weight
- 500m: 1.5% weight

This creates sharp contrast between POI-dense and sparse areas while maintaining
smooth gradients in transition zones.

3. Comparison Viewer (implemented)
----------------------------------
Addition: Side-by-side comparison viewer for evaluating different kernel parameters.

New CLI: compare.py
  python compare.py \
    --pbf file.pbf \
    --bbox "min_lon,min_lat,max_lon,max_lat" \
    --configs "name1:exponential:150" "name2:power_law:2:50" \
    --out output_compare

Features:
- 2-3 maps side by side with synchronized zoom/pan
- Shared color scale across all panels for fair comparison
- Panel headers showing kernel parameters
- Click any cell to see scores across all configs

4. Visualization: Fill Layer (implemented)
------------------------------------------
Problem: MapLibre heatmap layer changes appearance with zoom level.
Solution: Use polygon grid cells with fill layer instead of point heatmap.
Each grid cell is a square polygon that maintains consistent color at all zoom levels.

5. Power Law Kernel Formula (implemented)
-----------------------------------------
Problem: Original formula K(d) = 1/(d+d0)^p gave tiny values (~0.0001).
Solution: Normalized formula K(d) = 1/(1 + d/d0)^p

This gives:
- K(0) = 1.0 (same as exponential)
- Comparable decay rates when d0 matches lambda
- Power law tail behavior for p > 1

6. Grid Snapping Optimization (implemented)
-------------------------------------------
Problem: Grid point snapping to graph nodes used O(V) linear search per grid point,
resulting in O(V * n_grid) = O(n²) complexity. For large grids (17,750 points) with
large graphs (300k nodes), this was 5.3 billion comparisons.

Solution: Use scipy.spatial.cKDTree for O(n log n) snapping.

Measured speedup: 14x faster (106.9s → 7.7s on medium test)

7. Edge-Aware Snapping with Distance Threshold (implemented)
------------------------------------------------------------
Problem: Grid points in water (e.g., Charles River) were snapping to distant shore
nodes, creating artifacts - strange perpendicular lines of high scores bleeding
across the river. Two adjacent grid points in the river would snap to opposite
shores.

Solution: Edge-aware snapping with max distance threshold.
- Sample points along graph edges (every 20m) to detect distance to walkable paths
- Grid points farther than max_snap_distance from any edge get score = 0
- This correctly identifies water/inaccessible areas without explicit water polygons

Default: 75m (--max-snap parameter)
- 50m: Too aggressive, marks some valid areas (parks, plazas) as unreachable
- 75m: Good balance - river is cold, parks/plazas are scored
- 100m+: Noticeable bleeding from bridges

The snapping still uses nearest node for Dijkstra, but the edge distance check
ensures only truly walkable grid points are scored.

8. Indoor Corridor Support (implemented)
----------------------------------------
Addition: Walk network extraction now includes OSM indoor corridors.

The standard pyrosm walking network filter doesn't include `highway=corridor`,
which is used for indoor hallways in buildings with indoor mapping (airports,
malls, train stations).

extractor.py now:
1. Extracts standard walking network
2. Separately queries for highway=corridor features
3. Merges corridors into walk network if found

This enables proper walk-distance scoring inside large mapped buildings.
Most buildings don't have indoor mapping yet, but when they do, this will
automatically include the indoor paths in the walk graph.

9. Binary Output Format (implemented)
-------------------------------------
Problem: GeoJSON output files exceed 100MB for large grids, unsuitable for web serving.
Each grid cell stored as full GeoJSON Polygon feature with 5 coordinate pairs (~352 bytes/cell).
For 400k cells: ~136 MB.

Solution: Custom binary format with client-side polygon reconstruction.

Grid mode output:
- grid.json: Metadata (~500 bytes) with bounds, dimensions, UTM zone
- scores.bin: Raw Float32 array of scores in row-major order

Streets mode output:
- streets.json: Metadata with bounds and segment count
- segments.bin: Packed Float32 array (start_lon, start_lat, end_lon, end_lat, score per segment)

Size reduction:
- 272 cells: 1.5 KB binary vs 95.6 KB GeoJSON (63x smaller)
- 139,784 cells: 547 KB binary vs ~49 MB GeoJSON (90x smaller)

The HTML viewer loads binary data and reconstructs GeoJSON client-side using linear
interpolation (no proj4js dependency). Cell corners computed from bounds and grid dimensions.

Usage: --output-format binary (default: geojson)
